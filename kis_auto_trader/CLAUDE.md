# CLAUDE.md

이 저장소에서 작업할 때 따르는 행동 원칙. (2026-08-26, karpathy-guidelines +
superpowers 핵심 원칙을 참고해 이 프로젝트에 맞게 정리)

**전제**: 이건 모의투자가 아니라 실전(real) 계좌로 자동매매하는 프로그램이다.
코드 한 줄의 실수가 바로 실제 손실로 이어질 수 있으므로, 아래 원칙은 "느려도
안전하게"에 무게를 둔다. 사소한 작업(오타 수정 등)까지 매번 다 지킬 필요는
없고, 판단해서 적용한다.

## 1. 코딩 전에 먼저 생각한다

- 확신 없으면 추측하지 말고 물어본다. 여러 해석이 가능하면 그중 하나를
  조용히 골라서 진행하지 말고, 선택지를 먼저 제시한다.
- 더 단순한 방법이 있으면 그걸 먼저 말한다.
- 요청이 불명확하면 일단 멈추고 뭐가 불명확한지 짚어서 물어본다.

## 2. 단순하게 만든다

- 요청받은 것 이상을 만들지 않는다. 나중에 쓸모 있을 것 같다는 이유로
  미리 확장성/설정 옵션을 넣지 않는다.
- 일어날 수 없는 상황에 대한 예외처리를 만들지 않는다.
- 200줄로 짰는데 50줄로 될 것 같으면 다시 짠다.

## 3. 수술하듯 고친다

- 요청받은 부분만 건드린다. 옆에 있는 코드/주석/포맷을 "더 낫게" 고치지 않는다.
- 망가지지 않은 걸 리팩토링하지 않는다. 기존 스타일이 마음에 안 들어도 맞춘다.
- 내 변경 때문에 안 쓰이게 된 import/변수/함수만 정리한다. 원래 있던 죽은
  코드는 발견해도 지우지 말고 언급만 한다.
- 바뀐 줄 하나하나가 전부 실제 요청과 직접 연결돼야 한다.

## 4. 목표를 검증 가능하게 정의하고, 확인될 때까지 반복한다

- "버그 고쳐줘" → "재현하는 테스트를 먼저 만들고, 그게 통과하게 고친다"
- "기능 추가해줘" → "그 기능이 되는지/안 되는 경우까지 확인하는 테스트를 만들고 통과시킨다"
- 여러 단계짜리 작업은 시작 전에 짧게 계획을 말한다:
  ```
  1. [할 일] → 확인: [뭘로 검증할지]
  2. [할 일] → 확인: [뭘로 검증할지]
  ```
- **"코드를 고쳤으니 될 것이다"라고 말하지 않는다.** 실제로 돌려보거나
  재현 테스트를 통과시킨 뒤에만 "됐다"고 말한다. (2026-08-26, 이 프로젝트에서
  검증 없이 결과를 단정했다가 실제 계좌 손익 계산이 몇 주간 틀려있던 걸
  뒤늦게 발견한 적이 있다 - 반드시 지킬 것.)

## 5. 막힐 땐 추측 대신 체계적으로 디버깅한다

- 에러 메시지/로그를 먼저 정확히 읽는다. 추측으로 여러 개를 한꺼번에 고치지
  않고, 한 번에 하나씩 원인을 좁혀간다.
- 실제 계좌/실제 로그로 재현되는 문제는, 그 정확한 상황을 테스트로 재현한
  뒤에 고친다 - "아마 이래서 그럴 것"이라고 짐작만으로 고치지 않는다.

## 6. 이 프로젝트 특유의 규칙

- **완성된 파일 전체를 준다.** 일부만 바꾸는 조각(diff)이 아니라, 사용자가
  그대로 덮어쓸 수 있는 전체 파일로 준다.
- **검증 안 된 걸 사실처럼 말하지 않는다.** 실제로 안 돌려본 추측은
  "추측이다"라고 표시한다.
- 시간에 민감한 판단(장 마감 여부 등)을 하기 전에는 실제 현재 시각을 확인한다.
- 테스트/검증 스크립트는 세션 임시 폴더가 아니라 `tests/`에 커밋해서 다음에도
  재현 가능하게 남긴다.

다시 짜는 일이 줄고, 실수 후 수습하는 질문이 아니라 구현 전에 명확히 하는
질문이 먼저 나온다.
